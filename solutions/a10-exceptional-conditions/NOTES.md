# Solution notes: A10 Mishandling of Exceptional Conditions

- `AccessChecker::canExport()` now fails closed: on any `\Throwable` it logs `permission.check_failed` with the user id and the exception class (not the message, which can hold secrets) and returns `false`. A silent `return false` without the log is only half a fix, because the outage would go unnoticed.
- The exception renderer in `bootstrap/app.php` returns `{"error": "Something went wrong."}` with status 500 for unexpected exceptions. It returns `null` (let Laravel handle it) for `HttpExceptionInterface`, `ValidationException`, `AuthenticationException`, `AuthorizationException`, `ModelNotFoundException`, `TokenMismatchException` and `HttpResponseException`, so Laravel's normal handling keeps 404, 403, 422, 401 and 419 (expired CSRF token) intact and responses that code built itself are not replaced.
- Laravel already reports (logs) unhandled exceptions, so the closure does not need to log them again; it only has to stop leaking details. Call `report($e)` only for exceptions that you handle yourself.
- Keep `APP_DEBUG=false` in production (see A02) as a second layer; it is not a replacement for a safe handler.
- Checked against the Laravel 13.x error handling docs: `withExceptions(function (Exceptions $exceptions) { ... })` in `bootstrap/app.php`, `$exceptions->render(...)` with the exception type taken from the closure's type-hint (here `\Throwable`, so it is a catch-all), and "if the closure does not return a value, Laravel's default exception rendering will be utilized", which is what the `return null` branch relies on. The docs also state that Laravel already treats 404, 403 and 419 specially, which is why those exceptions are passed through. The exact exception class names come from the framework (`Illuminate\Session\TokenMismatchException`, `Illuminate\Http\Exceptions\HttpResponseException`, etc.) and are not listed on that docs page.

Stretch: monitor the `permission.check_failed` log entry and alert when it appears repeatedly, which signals a dependency outage. Add a request id to responses and log context so support can match a user's report with the entry.
